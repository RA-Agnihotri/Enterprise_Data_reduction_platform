1. Executive Summary

EDRP is a metadata-driven Snowflake framework that generates representative, reduced-volume datasets while preserving:

  • Referential integrity — zero orphaned foreign keys across all related tables
  • Categorical coverage — all distinct values of business-critical columns are retained
  • Statistical representation — proportional distributions maintained via stratified sampling
  • Business relationships — parent-child chains preserved even without physical PK/FK constraints

Key Design Principles

  • 100% Snowflake — No external infrastructure. All procedures, storage, AI, dashboards, and agents run inside Snowflake.
  • Metadata-driven — Configuration lives in tables, not code. Change behavior by updating rows, not procedures.
  • Selective reduction — Only tables registered in TABLE_INVENTORY with IS_ACTIVE=TRUE are processed.
  • Repeatable & auditable — Every execution is logged with job IDs, timing, row counts, and validation results.
  • Resume-from-failure — Failed jobs can be resumed, skipping already-created tables and picking up where they left off.
  • Real-time monitoring — Live progress tracking via CURRENT_TABLE and TABLES_PROCESSED updates visible in the Streamlit dashboard.
  • AI-powered — Cortex COMPLETE for relationship discovery, sensitivity classification, and validation summarization. Cortex Agent for natural language data queries.

4. Pipeline Execution Flow

1
SP_EXTRACT_METADATA(database, schema)
Auto-discovers tables and columns from INFORMATION_SCHEMA. Discovers join patterns from ACCESS_HISTORY (last 90 days). Detects declared FK constraints. Populates TABLE_INVENTORY, COLUMN_INVENTORY, and RELATIONSHIP_MAP.
↓
2
Manual Configuration
Review discovered tables. Set IS_ACTIVE=FALSE for tables you don't want. Add logical RELATIONSHIP_MAP entries for joins without physical FKs. Configure SAMPLING_STRATEGY and STRATIFY_COLUMNS for categorical coverage. Optionally run SP_AI_DISCOVER_RELATIONSHIPS for AI-suggested FKs. Optionally run SP_AI_CLASSIFY_SENSITIVITY for column-level sensitivity classification.
↓
3
SP_BUILD_DEPENDENCY_GRAPH(database, schema)
Builds a directed graph using NetworkX. Detects and breaks cycles. Computes topological sort → writes REDUCTION_ORDER. Auto-classifies ROOT tables (FULL_COPY) and LEAF tables (FK_CASCADE).
↓
4
SP_EXECUTE_REDUCTION(profile_name [, resume_job_id])
Reads REDUCTION_PROFILE for source/target routing. Processes tables in REDUCTION_ORDER. Applies strategy per table: FULL_COPY, SAMPLE, FK_CASCADE, or EXCLUDE. Updates CURRENT_TABLE and TABLES_PROCESSED in real time. Logs every table to REDUCTION_TABLE_LOG. Tracks created tables in TABLES_CREATED_LIST for rollback/resume. If a job fails mid-way, pass the failed JOB_ID as resume_job_id to pick up where it left off.
↓
5
SP_VALIDATE_REDUCTION(job_id)
Runs FK integrity checks (orphan count = 0). Logs row count ratios. Compares distribution deviation on fact table FK columns. Writes all results to VALIDATION_RESULTS. Updates job status to VALIDATED or VALIDATION_FAILED. Optionally call FN_AI_SUMMARIZE_VALIDATION(job_id) for an LLM-generated summary.

6. Sampling Techniques Guide

6.1 Overview of Techniques

TechniqueStrategySQL PatternBest ForPreserves Integrity?
FULL_COPY FULL_COPY CREATE TABLE target AS SELECT * FROM source Dimension/reference tables, lookup tables, small tables Yes — all rows retained
Random Bernoulli SAMPLE + RANDOM SELECT * FROM source SAMPLE BERNOULLI(10%) SEED(42) Large driver tables where categorical coverage is not critical Partial — rare values may be dropped
Stratified SAMPLE + STRATIFIED ROW_NUMBER PARTITION BY strata_cols, take N per stratum Tables where all distinct values of a column must be preserved (e.g., country codes, segments) Yes — at least 1 row per stratum guaranteed
FK Cascade FK_CASCADE SELECT DISTINCT child.* FROM source child INNER JOIN reduced_parent p ON child.FK = p.PK Fact/transaction tables that must align with already-reduced parent tables Yes — zero orphaned FKs by construction
Exclude EXCLUDE No SQL executed Tables not needed in the reduced dataset (staging, temp, archive) N/A

6.2 Random Bernoulli Sampling

How It Works

Each row is independently included with probability = SAMPLE_PERCENT/100. Snowflake's SEED parameter makes it deterministic — same seed + same data = same output.

CREATE OR REPLACE TABLE target.CUSTOMER AS
SELECT * FROM source.CUSTOMER
SAMPLE BERNOULLI (10) SEED (42);

When to Use

  • Large tables where you need a quick, statistically representative subset
  • Columns don't have rare categorical values that must be preserved
  • Performance testing (approximate volumes are sufficient)

Limitations

  • Rare values may be entirely excluded (a country with 3 customers has only a 27% chance of being sampled at 10%)
  • Actual output size varies slightly from the target percentage

6.3 Stratified Sampling

How It Works

Groups rows by STRATIFY_COLUMNS, then takes GREATEST(1, ROUND(group_size × pct/100)) rows per group. This guarantees at least 1 row per distinct combination of stratification columns.

-- Configuration:
UPDATE TABLE_INVENTORY SET
  SAMPLING_STRATEGY = 'STRATIFIED',
  STRATIFY_COLUMNS = 'C_BIRTH_COUNTRY'
WHERE TABLE_NAME = 'CUSTOMER';

-- Generated SQL (simplified):
WITH strata_counts AS (
  SELECT C_BIRTH_COUNTRY, COUNT(*) AS stratum_size,
         GREATEST(1, ROUND(COUNT(*) * 10 / 100.0)) AS sample_size
  FROM source.CUSTOMER GROUP BY C_BIRTH_COUNTRY
),
numbered AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY C_BIRTH_COUNTRY ORDER BY RANDOM(42)
  ) AS _rn FROM source.CUSTOMER
)
SELECT n.* EXCLUDE (_rn) FROM numbered n
JOIN strata_counts sc ON n.C_BIRTH_COUNTRY = sc.C_BIRTH_COUNTRY
WHERE n._rn <= sc.sample_size;

When to Use

  • Columns with rare but business-critical values (country codes, product categories, risk levels)
  • AI/ML validation — model training requires all classes represented
  • Regulatory testing — all regions/jurisdictions must be covered

Multi-Column Stratification

-- Preserve all combinations of country + customer segment
STRATIFY_COLUMNS = 'C_BIRTH_COUNTRY, C_PREFERRED_CUST_FLAG'

Warning: High-cardinality combinations can result in more rows than expected. If COUNTRY has 211 values and SEGMENT has 2 values, you guarantee at least 422 rows.

6.4 FK Cascade

How It Works

For each FK relationship where the parent was sampled (not full-copied), the child table is INNER JOINed to the reduced parent. This ensures every FK value in the child exists in the reduced parent — zero orphans by construction.

-- If CUSTOMER was sampled (10M from 100M), STORE_RETURNS gets:
CREATE OR REPLACE TABLE target.STORE_RETURNS AS
SELECT DISTINCT child.*
FROM source.STORE_RETURNS child
INNER JOIN target.CUSTOMER p0
  ON child.SR_CUSTOMER_SK = p0.C_CUSTOMER_SK;

Multiple FK Parents

If a fact table has FKs to multiple sampled parents, ALL are joined:

SELECT DISTINCT child.*
FROM source.CATALOG_RETURNS child
INNER JOIN target.CUSTOMER p0
  ON child.CR_REFUNDED_CUSTOMER_SK = p0.C_CUSTOMER_SK
INNER JOIN target.CUSTOMER p1
  ON child.CR_RETURNING_CUSTOMER_SK = p1.C_CUSTOMER_SK;

Smart Parent Detection

The engine only joins to parents that were actually sampled (SAMPLE or FK_CASCADE strategy). Parents with FULL_COPY are skipped since all their keys are present — no filtering needed.

9. Resume-from-Failure & Real-Time Progress

9.1 Resume-from-Failure

Problem

Large-scale reductions (21 tables, billions of rows) can fail mid-execution due to timeouts, resource limits, or transient errors. Without resume capability, the entire job must be re-run from scratch, re-processing tables that were already completed.

Solution

SP_EXECUTE_REDUCTION accepts an optional RESUME_JOB_ID parameter. When provided, the procedure:

  1. Loads the TABLES_CREATED_LIST from the failed job (JSON array of successfully created table names)
  2. Skips tables already in that list during processing
  3. Creates a new JOB_ID for the resume run (preserving audit trail)
  4. Processes only the remaining tables
-- Original run fails at table 18 of 21
CALL EDRP_APP.SP_EXECUTE_REDUCTION('POC_10PCT_REDUCTION');
-- Job 401 created, status = FAILED, TABLES_CREATED_LIST has 17 tables

-- Resume from where it left off
CALL EDRP_APP.SP_EXECUTE_REDUCTION('POC_10PCT_REDUCTION', 401);
-- Job 501 created, skips 17 tables, processes remaining 4
-- Status = COMPLETED
Requirements for resume: The failed job must have TABLES_CREATED_LIST populated (not NULL or empty). Jobs that failed before processing any tables cannot be resumed — they must be re-run.

9.2 Real-Time Progress Tracking

How It Works

The reduction engine updates two columns in REDUCTION_JOB_LOG after each table:

  • CURRENT_TABLE — set to the table name before processing begins; cleared after completion
  • TABLES_PROCESSED — incremented by 1 after each table successfully completes

Live Monitoring Query

-- Run this in a separate session while a reduction is executing
SELECT JOB_ID, JOB_STATUS, CURRENT_TABLE, 
       TABLES_PROCESSED || '/' || TOTAL_TABLES AS PROGRESS,
       ROUND(TABLES_PROCESSED / NULLIF(TOTAL_TABLES, 0) * 100, 1) AS PCT
FROM DATA_REDUCTION_POC.EDRP_METADATA.REDUCTION_JOB_LOG
WHERE JOB_ID = (SELECT MAX(JOB_ID) FROM DATA_REDUCTION_POC.EDRP_METADATA.REDUCTION_JOB_LOG);

Streamlit Integration

The "Execute Reduction" page in the Streamlit dashboard displays a live progress bar, current table name, and table-by-table status breakdown using these columns.

15.3 Known Exceptions

WEB_PAGE orphan rows: WEB_PAGE is configured as FULL_COPY (ROOT) but has a FK relationship to CUSTOMER (which is SAMPLE). Since WEB_PAGE retains all rows and CUSTOMER is reduced, ~1,300 orphaned WEB_PAGE.WP_CUSTOMER_SK values exist. This is a known acceptable tradeoff — WEB_PAGE is a dimension table that should remain complete. Fix: either add a FK_CASCADE for WEB_PAGE, or accept the partial orphan in this specific relationship.
